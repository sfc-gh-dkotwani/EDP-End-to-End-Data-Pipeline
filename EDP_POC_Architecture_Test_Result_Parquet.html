1. Overview

This POC implements an end-to-end data pipeline for BlackRock's transaction data on Snowflake. Parquet files are ingested into a schema-flexible VARIANT mirror layer, validated across three quality gates, transformed into typed staging tables via dbt, and surfaced in an auto-refreshing presentation layer with derived analytics columns.

The pipeline runs as a 6-step task DAG (every 4 hours or on-demand), with 42 data quality checks spanning completeness, format, domain, referential integrity, cross-table consistency, and freshness. All quality results are logged to an audit layer, and email alerts fire on any failure.

Each step depends on the previous one succeeding. If any quality gate fails, the pipeline halts and an alert is sent.

3. Data Ingestion

How Data Enters Snowflake

Parquet files are uploaded to an internal Snowflake stage. The ingestion task runs a single COPY INTO statement that loads each Parquet row directly as a VARIANT object. Because Parquet is self-describing (column names are embedded in the file metadata), no positional mapping is needed:

COPY INTO TRANSACTIONS (RAW_DATA, _FILENAME, _FILE_ROW_NUM, _BATCH_ID)
FROM (
    SELECT
        $1,
        METADATA$FILENAME,
        METADATA$FILE_ROW_NUMBER,
        '<batch_uuid>'
    FROM @RAW_STAGE (FILE_FORMAT => 'PARQUET_FMT')
)
ON_ERROR = 'SKIP_FILE'
FORCE    = FALSE

Parquet $1 is a VARIANT object that automatically contains all column names and values from the file. Adding, removing, or reordering columns in the source file has no effect on the ingestion mapping.

Parquet File Format

The pipeline uses a named file format for consistent Parquet handling:

CREATE FILE FORMAT IF NOT EXISTS PARQUET_FMT
    TYPE = 'PARQUET'
    COMMENT = 'Parquet format for VARIANT mirror ingestion';

What Gets Captured

ColumnWhat It Stores

Error Handling

  • Corrupt files are skipped (ON_ERROR = SKIP_FILE) — the rest of the batch loads successfully
  • New columns in the Parquet file appear as new keys in the VARIANT — existing downstream logic is unaffected
  • Already-loaded files are not re-processed (FORCE = FALSE) — prevents duplicate data
  • Null representations (NULL, empty string, N/A, \N) are normalized to SQL NULL

4. Data Layers

graph LR
    A[Parquet on Stage] -->|COPY INTO| B[Mirror - Raw VARIANT]
    B -->|dbt extract + type cast| C[Staging - Typed Columns]
    C -->|Dynamic Table| D[Presentation - Enriched]

Mirror Layer RAW

Immutable landing zone. Every Parquet row is preserved exactly as received in a VARIANT object with the original column names. No type casting, no filtering, no deduplication. This provides full fidelity for audit and replay if downstream issues are discovered.

Quality gate: 17 checks validate completeness, format, type casting, domain, uniqueness, and schema immediately after load.

Staging Layer TYPED

Managed by dbt (incremental materialization). Extracts typed columns from the VARIANT mirror:

  • Type casting: AMOUNT to DECIMAL(18,4), TXN_DATE to DATE, etc.
  • Cleansing: uppercase and trim on CURRENCY and STATUS
  • Filtering: rows with null TXN_ID, AMOUNT, or TXN_DATE are excluded
  • Incremental: only processes newly arrived rows

Quality gate: 13 checks validate schema structure, referential integrity against reference tables (accounts and instruments), and data provenance.

Presentation Layer ENRICHED

A Dynamic Table that auto-refreshes from staging. Adds derived analytics columns:

  • TXN_MONTH, TXN_YEAR, TXN_DAY_OF_WEEK — time dimensions for reporting
  • RUNNING_POSITION_BY_ACCOUNT — cumulative position (running total of AMOUNT per account)

Quality gate: 17 checks validate derived columns are correct, and that totals, row counts, and dimensions match between staging and presentation.

Reference Layer

Lookup tables for Accounts (500) and Instruments (2,000). Every ACCOUNT_ID and INSTRUMENT_ID in staging must exist in the corresponding reference table.

Audit Layer

Records the outcome of every quality check, every pipeline run, and performance benchmarks. Key tables:

  • TDQ_RESULTS — per-layer quality check results: batch ID, layer (ML/STG/SDM), pass/fail, failed details, row count, and execution time
  • PIPELINE_RUNS — one row per pipeline execution: batch ID, status, which quality gates passed
  • STRESS_TEST_RESULTS — per-task timing for each pipeline run: phase, start/end timestamps, duration, rows processed, warehouse size
  • PERFORMANCE_BENCHMARKS — rows/sec metrics per layer and warehouse size

Finalizer — Automated Timing Capture

The last task in the DAG (FINALIZER_TASK_V2) calls the RUN_FINALIZER_V2() stored procedure, which automatically captures per-task timing without manual intervention. It derives data from three sources:

  • TDQ_RESULTS — each quality SP (ML TDQ, STG BDQ, SDM BDQ) writes RUN_AT (completion timestamp) and EXECUTION_TIME_SECS. Start time is computed as RUN_AT - EXECUTION_TIME_SECS.
  • COPY_HISTORY — the earliest LAST_LOAD_TIME from the most recent COPY INTO provides the ingest start time.
  • SHOW WAREHOUSES — warehouse sizes are looked up dynamically at runtime (not hardcoded), so resizing a warehouse is automatically reflected in subsequent pipeline runs.

Gap-derived timing: dbt duration is the gap between ML TDQ end and STG BDQ start; ingest duration is the gap between COPY start and ML TDQ start.

The finalizer writes 6 rows to STRESS_TEST_RESULTS: one for each of the 5 pipeline tasks plus a TOTAL_PIPELINE_E2E summary row.

5. Data Quality Checks

How Validation Works

Data quality checks run at three layers (Mirror, Staging, Presentation). Each layer uses the same two-phase pattern: Snowpark computes metrics server-side, then Great Expectations validates the results.

Snowpark Lazy Execution — Why It Matters for Performance

Snowpark's DataFrame API builds a SQL query plan in Python without executing anything until .collect() is called. This means all checks at a layer — null counts, format validations, domain checks, type-cast failures — are combined into a single SQL SELECT with multiple COUNT_IF aggregations. Snowflake executes this as one table scan, regardless of how many individual checks are defined.

# Python (Snowpark) — builds query plan, does NOT execute yet
metrics_df = batch_df.agg(
    COUNT_IF(col("TXN_ID").is_null()).alias("NULL_TXN_ID"),
    COUNT_IF(col("AMOUNT").is_null()).alias("NULL_AMOUNT"),
    COUNT_IF(~col("CURRENCY").isin(["USD","EUR","GBP"])).alias("BAD_DOMAIN_CURRENCY"),
    # ... 15+ more checks ...
    count("*").alias("TOTAL_ROWS"),
)

# NOW executes — Snowflake runs ONE optimized query
metrics_row = metrics_df.collect()[0]
# Result: {"NULL_TXN_ID": 0, "NULL_AMOUNT": 0, "BAD_DOMAIN_CURRENCY": 0, ...}

Without lazy execution, each check would require a separate query and a separate table scan. With 15+ checks per layer and millions of rows, this would multiply query time significantly. The lazy approach reduces this to 2 scans per layer (one for batch metrics, one for cross-batch or cross-table joins).

Great Expectations (GX) — How It Is Used

GX does not scan any data directly. Instead, it validates the pre-computed metrics row from Snowpark. This is a key optimization: GX operates on a single-row Pandas DataFrame containing aggregated counts, not millions of raw records.

# The metrics row from Snowpark becomes a 1-row Pandas DataFrame
metrics_pdf = pd.DataFrame([{"NULL_TXN_ID": 0, "BAD_DOMAIN_CURRENCY": 0, "TOTAL_ROWS": 1000000}])

# GX validates each metric: "NULL_TXN_ID should be between 0 and 0" (i.e., must equal 0)
suite.add_expectation(
    ExpectColumnValuesToBeBetween(column="NULL_TXN_ID", min_value=0, max_value=0)
)
suite.add_expectation(
    ExpectColumnValuesToBeBetween(column="TOTAL_ROWS", min_value=1, max_value=None)
)

# Run GX validation — instant (1 row, no data scan)
result = validation_definition.run(batch_parameters={"dataframe": metrics_pdf})

GX provides:

  • Structured results — each check has a category, description, pass/fail status, and observed value
  • Expectation suites — checks are defined declaratively and can be versioned, shared, and audited
  • Consistent reporting — all three layers use the same GX validation pattern, making results comparable

Alternative Approaches: Native SQL and DMFs

Every quality check in the pipeline can also be implemented without GX or Snowpark. The code includes inline comments showing both alternatives:

Option A: Native SQL

Replace the entire Snowpark + GX pattern with a single SQL query:

-- Direct SQL equivalent of the Snowpark aggregation
SELECT
    COUNT_IF(RAW_DATA:TXN_ID IS NULL) AS null_txn_id,
    COUNT_IF(RAW_DATA:AMOUNT IS NULL) AS null_amount,
    COUNT_IF(NOT RAW_DATA:CURRENCY::VARCHAR IN ('USD','EUR','GBP','JPY','CHF')) AS bad_domain_currency,
    COUNT(*) AS total_rows
FROM MIRROR.TRANSACTIONS
WHERE _BATCH_ID = :batch_id;

Tradeoff: Identical performance (same single scan). Loses GX's structured reporting and expectation management. Best for teams that prefer pure SQL and build their own alerting.

Option B: Data Metric Functions (DMFs)

Attach checks directly to the table. Snowflake runs them automatically when data changes — no stored procedures, no tasks, no warehouse scheduling:

-- Attach a built-in DMF to the table
ALTER TABLE STAGING.STG_TRANSACTIONS
    ADD DATA METRIC FUNCTION SNOWFLAKE.CORE.NULL_COUNT ON (TXN_ID);

-- Snowflake runs it automatically after data changes
ALTER TABLE STAGING.STG_TRANSACTIONS
    SET DATA_METRIC_SCHEDULE = 'TRIGGER_ON_CHANGES';

Tradeoff: Zero operational overhead (serverless, automatic). Cannot scope checks to a specific batch — DMFs validate the entire table. Best for table-level health monitoring alongside batch-scoped checks.

Recommended Approach Use Snowpark + GX (current implementation) for batch-scoped and cross-table checks that need structured reporting. Use DMFs alongside for continuous, table-level monitoring. Use native SQL if the team prefers to avoid Python dependencies entirely.

6. Schema Change Handling

Because Parquet files are self-describing (columns are identified by name, not position), the pipeline is resilient to most schema changes:

What ChangesImpactDetected ByAction Required
New column added (any position) Safe — new key appears in VARIANT automatically. Existing downstream extraction is unaffected. N/A (no failure) When ready, update the dbt model to extract the new column.
Column removed Detected — the removed key is absent from VARIANT. Downstream extraction returns NULL. Completeness checks fail (null count > 0) Update the dbt model and quality checks to reflect the new column set.
Column reordered Safe — Parquet identifies columns by name, not position. Order is irrelevant. N/A (no failure) None.
Column renamed Detected — old key disappears (extraction returns NULL), new key appears as a new VARIANT field. Completeness checks fail for the old column name Update the dbt model to use the new column name.
Column data type changed Detected — TRY_CAST in the dbt model returns NULL for incompatible values. Type-cast checks in ML TDQ and completeness checks in staging Update the dbt model cast if the new type is intentional.

Observations

  • SDM BDQ is the bottleneck (54% of total) — dominated by the Dynamic Table refresh.
  • INGEST + dbt together accounted for 38% — both are I/O-heavy operations (COPY INTO and incremental MERGE).
  • ML TDQ + STG BDQ are lightweight (21 sec combined, 6%) — Snowpark lazy aggregation keeps quality checks fast even at 322.5M rows.
  • Throughput: ~880K rows/sec end-to-end, ~4.1M rows/sec for ingestion alone.
